# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CleanAir is STM32 firmware (the `.ioc`, the build and the schematic target the STM32G474 on a WeAct G474CE Long board, see the README pin plan; the older STM32F446RE Nucleo-64 files are kept for reference only; its pin table, power notes and board damage note are in `doc/board_stm32f466.md`, and the README describes only the G474) for an AC vent fan controller that reads air-quality sensors (SPS30 particulates, BME680 + Bosch BSEC2, MQ131 ozone, MiCS-4514 CO/NO2) and phase-cuts an AC fan motor via a TRIAC. Each sensor reading is turned into a danger level (Off / Ventilate / Evacuate) and the fan follows the worst one; the buzzer sounds at Evacuate. See `README.md` for the hardware architecture, pin mapping, and control-loop diagrams — read it before making hardware-facing changes (peripheral assignments, timing, safety thresholds).

## Build

This is a bare-metal ARM Cortex-M4 project cross-compiled with `arm-none-eabi-gcc`/`g++` (must be on `PATH`) and built with CMake + Ninja via presets:

```sh
cmake --preset Debug        # or Release
cmake --build build/Debug   # or build/Release
```

There is no test suite, linter, or `main()` entry point runnable on a host — this firmware only runs on the target MCU. "Testing" a change means building successfully and, when touching sensor/motor logic, reasoning through the FreeRTOS task and ISR flow described below and in `README.md`.

Flashing/debugging is done through CLion's ST-Link integration (this is a CLion-managed project, per `build/Debug/.gitignore` and `.idea/`); there is no checked-in flash script.

Do not hand-edit HAL init code generated by STM32CubeMX (`Core/Src/main.c`, `stm32g4xx_hal_msp.c`, `cmake/stm32cubemx/`, `.mxproject`, `clear-air.ioc`) — regenerate from `clear-air.ioc` in STM32CubeMX instead, since manual edits are overwritten on the next regeneration. Peripheral/pin changes belong in the `.ioc` file first.

## Hardware schematic

The wiring schematic is `hardware/WeAct-G474CE-Long/clearair.kicad_sch` (KiCad 10, A2 sheet). `hardware/Nuclio-F466RE/clearair.kicad_sch` is the old NUCLEO-F446RE schematic, kept for reference: do not edit it. The WeAct board and sensor-module symbols come from the user's global KiCad libraries (`FullModules`, `UvLibrary`); copies are embedded in the schematic. Project-only symbols live in `hardware/WeAct-G474CE-Long/clearair.kicad_sym` (library `clearair`, listed in the project `sym-lib-table`). When you mention a pin, give the G474 pin. Every pin is wired with drawn lines: do not replace wires with label-only nets. When a pin assignment changes in `clear-air.ioc`, update the schematic, the README pin table, and the README power budget (Power & Logic Integration → Power Budget) together.

`hardware/WeAct-G474CE-Long/perfboard_wiring.md` is generated by `hardware/tools/perfboard_wire_list.py` and checked by `hardware/tools/perfboard_verify.py` (see `hardware/tools/README.md`): regenerate it after a schematic or PCB change, never edit it. Its data come from KiCad itself: wire gauge (IPC-2221 current of the track width) and wire color from the net classes in `clearair.kicad_pro`, net names from net labels on the schematic wires, logic-high straps from symbol pin types, later-stage parts from DNP, bus strips from board-only footprints in the PCB. Do not add custom fields or config files for it.

## Architecture

- **C vs C++ boundary:** CubeMX generates C code (`Core/Src/main.c`, HAL, FreeRTOS task stubs). All application logic lives in C++ under `device/*` and is wired in via `extern "C"` task-handler trampolines defined in `Core/Src/cpp_main.cpp`. Each `xTaskHandler` function (e.g. `bmeTaskHandler`) suspends itself immediately, then blocks in the corresponding `SensorX::taskLoop()` — the task is later resumed explicitly once `configure()` succeeds in `appStartDefaultTask`.
- **Per-sensor modules (`device/<name>/`):** Each sensor/actuator is its own static CMake library (`bme68x`, `co1no2`, `fanmotor`, `o3sensor`, `particle`) with `inc/` and `src/`, built by `device/scope-share.cmake`'s `STM_SET_LIBNAME()` macro (library name = directory name). A module typically has a `task_*` class (owns the FreeRTOS task loop, derives from `BaseDeviceTask` in `device/include/base_device_task.h`) and, where hardware init is nontrivial, a `bridge_*` free function that wires the vendor driver to a HAL peripheral handle (see `bridge_bme680.cpp`, `bridge_particle.cpp`).
- **BaseDeviceTask contract:** every sensor task class implements `configure(...)` (hardware bring-up, returns success) and `[[noreturn]] taskLoop()`. `setup()` binds the FreeRTOS thread ID and the shared message queue handle.
- **Shared message queue:** all sensor tasks publish readings onto one FreeRTOS queue (`SensorEventsHandle`) as `CommonMessage` (`Core/Inc/event_message.h`) — a tagged union (`UniqueID` + payload struct per sensor, defined in `event_data.h`). `mainSensorsMsgLoop` in `Core/Src/control_center.cpp` is the single consumer that dispatches on `msg.id`. Aggregate/derived sensor state (temperature, IAQ, O3, PM2.5/PM10, etc.) is collected into `CollectedAirData` (`Core/Inc/collected_data.h`).
- **Sensor-level fan control (`Core/Src/control_center.cpp`):** each reading updates only its own metrics in a `MetricLevels` struct. Each metric has `LevelThresholds` (`fanOff`, `fanOn`, `fanMax`, `evacuate`, in the metric's own unit) that give a `Severity` (a `DangerLevel` plus a requested fan percent). `fanOff` is the hysteresis point for a running fan. At the end of every loop pass, `evaluateLevels()` takes the worst level and the highest fan percent across all metrics, runs the evacuate alarm (`updateAlarm()`: buzzer `BUZZER_IN` on 60 s, then off 30 s / on 10 s repeating while the air stays at `Evacuate`; if it drops below during a pause, two sequences of three 2 s beeps (6 s apart) signal safe and the alarm stops; timings and pattern are constants at the top of the alarm code), and calls `ControllerFanMotor::speedPercent()`. A fan that turns on from off first runs at 100% for `FAN_KICKSTART_MS`, so the loop uses a queue timeout while a spin-up or an alarm step runs. The MQ131 thresholds and `FAN_KICKSTART_MS` are placeholders until measured. The fan is an 8" 80 W capacitor-run AC motor; `TRIAC_MIN_POWER_DELAY_US` in `device/fanmotor` (5700, about 60% of mains RMS at the 50% setting) is an estimate to confirm on the bench, and `speedPercent()` maps linearly to the firing delay, not to power. The README section "Sensor-Level Fan Control" documents this with diagrams: update it when this logic changes.
- **Gas sensor heaters:** the MQ131 heater needs a constant 5 V, so the module VCC and GND go straight to the 5 V rail and GND and the firmware does not switch it (`PB12` is unused; the `.ioc` may still list it as `MQ131_PREHEAT` until you remove it there). The MQ131 sends no readings for 48 h on a cold boot (30 min on a warm restart, an estimate: the datasheet gives no value), so ozone cannot raise the fan level during that time. The MiCS-4514 heaters run on constant power from the module; its `PRE` (boost) pin is tied to GND and the firmware has no boost.
- **AC phase control (hardware real-time path, bypasses RTOS):** Lives entirely in `device/fanmotor` (`ControllerFanMotor`), not `cpp_main.cpp`. `HAL_GPIO_EXTI_Callback` (defined in `task_fanctrl.cpp`) fires on the zero-cross interrupt (`ZC_INPUT_Pin`) and calls `onZeroCross()`, which resets `TIM3`'s counter, loads the current phase delay into `TIM3->ARR`, and starts `TIM3`'s update interrupt. `TIM3_IRQHandler` (in `stm32g4xx_it.c`) calls the free function `FanMotorOnTimerFired()` (the `extern` declaration is in the `USER CODE Includes` block and the call is in the `TIM3_IRQn 1` block, so both survive CubeMX regeneration; if the call is lost the TRIAC never fires), which invokes `onGateCompareMatch()` to pulse the TRIAC gate pin — this is the direct ISR-to-timer path that fires the TRIAC gate; it does not go through the message queue or a FreeRTOS task.
- **80 mm fan PWM and tach (peripherals configured, no device module yet):** `TIM1` generates the 25 kHz fan PWM (CH1 on `PA8` `FAN_FRONT_PWM`, CH2 on `PA9` `FAN_REAR_PWM`, prescaler 0, period 6799 at 170 MHz). `TIM2` captures the tach signals (CH1 on `PA5` `FAN_FRONT_TACH`, CH2 on `PB3` `FAN_REAR_TACH`) as plain rising-edge input capture with a 1 µs tick; it is 32-bit and its interrupt is enabled at priority 5. `MX_TIM1_Init`/`MX_TIM2_Init` are generated, but nothing starts the channels (`HAL_TIM_PWM_Start`, `HAL_TIM_IC_Start_IT`) or implements `HAL_TIM_IC_CaptureCallback` yet. Put that in its own `device/` module, not in `cpp_main.cpp`. RPM = 60,000,000 / (pulses per revolution × period in µs).
- **Vendor drivers** (`Drivers/BME68x`, `Drivers/BSEC`, `Drivers/SPS30`, `Drivers/BSP`, `Drivers/CMSIS`, `Drivers/STM32G4xx_HAL_Driver`) and third-party middleware (`Middlewares/Third_Party`, FreeRTOS) are pulled in as-is; treat them as read-only unless specifically asked to update a driver.
- **Debug tracing:** `device/include/logger.h` provides `METHODTRACE`/`METHODLOG`/`METHODLOGF` macros (no-ops outside Debug builds) built on header-only `fmt` (fetched via `FetchContent` only in Debug builds — Release has no `fmt` dependency).
