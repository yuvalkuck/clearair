# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CleanAir is STM32 firmware (the `.ioc` and the build now target the STM32G474, see the README pin plan; the schematic still shows the STM32F446RE Nucleo-64) for an AC vent fan controller that reads air-quality sensors (SPS30 particulates, BME680 + Bosch BSEC2, MQ131 ozone, MiCS-4514 CO/NO2) and phase-cuts an AC fan motor via a TRIAC. Each sensor reading is turned into a danger level (Off / Ventilate / Evacuate) and the fan follows the worst one; the buzzer sounds at Evacuate. See `README.md` for the hardware architecture, pin mapping, and control-loop diagrams — read it before making hardware-facing changes (peripheral assignments, timing, safety thresholds).

## Build

This is a bare-metal ARM Cortex-M4 project cross-compiled with `arm-none-eabi-gcc`/`g++` (must be on `PATH`) and built with CMake + Ninja via presets:

```sh
cmake --preset Debug        # or Release
cmake --build build/Debug   # or build/Release
```

There is no test suite, linter, or `main()` entry point runnable on a host — this firmware only runs on the target MCU. "Testing" a change means building successfully and, when touching sensor/motor logic, reasoning through the FreeRTOS task and ISR flow described below and in `README.md`.

Flashing/debugging is done through CLion's ST-Link integration (this is a CLion-managed project, per `build/Debug/.gitignore` and `.idea/`); there is no checked-in flash script.

Do not hand-edit HAL init code generated by STM32CubeMX (`Core/Src/main.c`, `stm32g4xx_hal_msp.c`, `cmake/stm32cubemx/`, `.mxproject`, `clear-air.ioc`) — regenerate from `clear-air.ioc` in STM32CubeMX instead, since manual edits are overwritten on the next regeneration. Peripheral/pin changes belong in the `.ioc` file first.

## Hardware schematic

The wiring schematic is `hardware/Nuclio-F466RE/clearair.kicad_sch` (KiCad 10, A2 sheet). The NUCLEO-F446RE and sensor-module symbols come from the user's global KiCad libraries (`FullModules`, `UvLibrary`); copies are embedded in the schematic. Every pin is wired with drawn lines: do not replace wires with label-only nets. When a pin assignment changes in `clear-air.ioc`, update the schematic, the README pin table, and the README power budget (Power & Logic Integration → Power Budget) together.

## Architecture

- **C vs C++ boundary:** CubeMX generates C code (`Core/Src/main.c`, HAL, FreeRTOS task stubs). All application logic lives in C++ under `device/*` and is wired in via `extern "C"` task-handler trampolines defined in `Core/Src/cpp_main.cpp`. Each `xTaskHandler` function (e.g. `bmeTaskHandler`) suspends itself immediately, then blocks in the corresponding `SensorX::taskLoop()` — the task is later resumed explicitly once `configure()` succeeds in `appStartDefaultTask`.
- **Per-sensor modules (`device/<name>/`):** Each sensor/actuator is its own static CMake library (`bme68x`, `co1no2`, `fanmotor`, `o3sensor`, `particle`) with `inc/` and `src/`, built by `device/scope-share.cmake`'s `STM_SET_LIBNAME()` macro (library name = directory name). A module typically has a `task_*` class (owns the FreeRTOS task loop, derives from `BaseDeviceTask` in `device/include/base_device_task.h`) and, where hardware init is nontrivial, a `bridge_*` free function that wires the vendor driver to a HAL peripheral handle (see `bridge_bme680.cpp`, `bridge_particle.cpp`).
- **BaseDeviceTask contract:** every sensor task class implements `configure(...)` (hardware bring-up, returns success) and `[[noreturn]] taskLoop()`. `setup()` binds the FreeRTOS thread ID and the shared message queue handle.
- **Shared message queue:** all sensor tasks publish readings onto one FreeRTOS queue (`SensorEventsHandle`) as `CommonMessage` (`Core/Inc/event_message.h`) — a tagged union (`UniqueID` + payload struct per sensor, defined in `event_data.h`). `mainSensorsMsgLoop` in `Core/Src/control_center.cpp` is the single consumer that dispatches on `msg.id`. Aggregate/derived sensor state (temperature, IAQ, O3, PM2.5/PM10, etc.) is collected into `CollectedAirData` (`Core/Inc/collected_data.h`).
- **Sensor-level fan control (`Core/Src/control_center.cpp`):** each reading updates only its own metrics in a `MetricLevels` struct. Each metric has `LevelThresholds` (`fanOff`, `fanOn`, `fanMax`, `evacuate`, in the metric's own unit) that give a `Severity` (a `DangerLevel` plus a requested fan percent). `fanOff` is the hysteresis point for a running fan. At the end of every loop pass, `evaluateLevels()` takes the worst level and the highest fan percent across all metrics, drives the buzzer (`BUZZER_IN`) at `Evacuate`, and calls `ControllerFanMotor::speedPercent()`. A fan that turns on from off first runs at 100% for `FAN_KICKSTART_MS`, so the loop uses a queue timeout while a spin-up runs. The MQ131 thresholds, `FAN_KICKSTART_MS` and the fan minimum delay are placeholders until measured. The README section "Sensor-Level Fan Control" documents this with diagrams: update it when this logic changes.
- **AC phase control (hardware real-time path, bypasses RTOS):** Lives entirely in `device/fanmotor` (`ControllerFanMotor`), not `cpp_main.cpp`. `HAL_GPIO_EXTI_Callback` (defined in `task_fanctrl.cpp`) fires on the zero-cross interrupt (`ZC_INPUT_Pin`) and calls `onZeroCross()`, which resets `TIM3`'s counter, loads the current phase delay into `TIM3->ARR`, and starts `TIM3`'s update interrupt. `TIM3_IRQHandler` (in `stm32g4xx_it.c`) calls the free function `FanMotorOnTimerFired()`, which invokes `onGateCompareMatch()` to pulse the TRIAC gate pin — this is the direct ISR-to-timer path that fires the TRIAC gate; it does not go through the message queue or a FreeRTOS task.
- **Vendor drivers** (`Drivers/BME68x`, `Drivers/BSEC`, `Drivers/SPS30`, `Drivers/BSP`, `Drivers/CMSIS`, `Drivers/STM32F4xx_HAL_Driver`) and third-party middleware (`Middlewares/Third_Party`, FreeRTOS) are pulled in as-is; treat them as read-only unless specifically asked to update a driver.
- **Debug tracing:** `device/include/logger.h` provides `METHODTRACE`/`METHODLOG`/`METHODLOGF` macros (no-ops outside Debug builds) built on header-only `fmt` (fetched via `FetchContent` only in Debug builds — Release has no `fmt` dependency).
